# 地图库生命周期由共享核心维护

日期：2026-08-30 · 状态：Accepted

## 背景

Map Library 已同时运行在公开网站与本地桌面模式中。浏览器使用 IndexedDB 并在失败时回退到当前会话缓存；桌面模式通过本地 HTTP 接口把地图和组织状态写入文件系统。随着地图导入、永久编号、文件夹整理与整库备份逐步加入，地图记录规整、地图库状态规整、备份校验和冲突合并规则分别出现在界面脚本与本地存储模块中。同一业务行为因此存在多个维护权威，浏览器端测试又主要通过界面源码断言间接覆盖，存储后端之间容易发生语义漂移。

## 决定

1. 建立浏览器与 Node 均可消费的 Map Library 共享核心，作为地图记录、永久编号账本、组织状态、备份校验与冲突合并规则的唯一权威。
2. 共享核心提供少量面向完整行为的接口；地图记录和组织状态的内部规整辅助函数不作为界面或存储后端的长期接口。
3. IndexedDB、当前会话缓存、本地 HTTP 与文件系统只负责读取、写入和删除。它们不自行判断地图是否合法，也不复制备份或冲突处理规则。
4. 界面脚本只负责交互状态、展示和调用 Map Library；本地服务只负责 HTTP 传输与存储适配器装配。
5. 迁移保持既有 schema、IndexedDB 数据库与 store 名称、本地文件位置、HTTP 路径以及故障回退行为不变，不要求用户执行数据迁移。
6. 共享行为在最高可用缝上以同一组合同测试验证；各存储适配器另行验证自身的持久化、删除与失败行为。

## 取舍

- 本次只集中既有行为，不重新设计地图冲突命名、文件夹合并、损坏记录跳过或故障提示语义。
- 不引入 bundler 或 ESM-only 运行时；共享核心必须继续支持普通 `<script>` 加载与 Node 消费。
- 不把地图渲染、Map Integration 或 Paper Import 纳入 Map Library，以免核心接口重新膨胀。
- 迁移采用逐步替换并保留兼容入口，避免一次宽改动同时破坏浏览器、桌面模式和既有测试。

## 后果

- 地图导入、组织、导出和恢复在浏览器与桌面模式中共享同一套业务规则。
- 新增存储后端只需实现持久化适配器，不再复制地图或备份语义。
- 界面脚本与本地服务会缩小，但既有数据和公开接口保持可用。
- 后续改变 Map Library 的冲突或恢复语义时，只需修改共享核心及其合同测试。
